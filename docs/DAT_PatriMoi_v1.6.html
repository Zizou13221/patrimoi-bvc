1 Contexte et portée

PatriMoi est une application iOS de suivi de patrimoine personnel destinée aux Marocains résidant au Maroc ou à l'étranger. Elle couvre 8 catégories d'actifs : liquidités (espèces DH + 18 devises), banque (comptes courants/épargne), compte sur carnet, PEA (Bourse de Casablanca), compte-titres, or, immobilier, et transport (véhicules avec dépréciation automatique).

L'application propose deux modes :

  • Mode démo — données INIT (~1,5 M DH) pré-remplies, aucun compte requis, persistance locale uniquement (MMKV)
  • Mode connecté — compte Supabase, sync cloud, snapshots historiques, abonnement PatriMoi+ (49 DH/mois)

Ce DAT décrit la version 1.6, état de l'art de juillet 2026. Il couvre l'existant déployé — pas les évolutions futures.

2 Vue d'ensemble de l'architecture

PatriMoi suit une architecture client-heavy, BaaS-backed : toute la logique métier tourne dans le client React Native ; le backend (Supabase) assure uniquement la persistance, l'authentification, et le cache des données de marché.

Diagramme C4 — Niveau contexte (v1.6)
Principe directeur

Le client est la source de vérité pour les données utilisateur. Supabase est la sauvegarde cloud, pas un ORM. Toutes les mutations transitent par l'outbox MMKV — Supabase reçoit une copie asynchrone.

Le choix de rester sur l'Old Architecture est intentionnel : la New Architecture (JSI/Fabric) impose une réécriture des native modules et n'apporte pas de gains utilisateur mesurables pour cette app à dominante formulaire. La migration sera envisagée en v2.0.

Hermes est le seul moteur supporté. Deux contraintes importantes :

  • crypto.getRandomValues() disponible depuis Hermes 0.13 / RN 0.74 → fallback Math.random() inclus dans _generateKey() et _randomSalt()

4 Couche stockage

PatriMoi utilise une architecture de stockage en trois niveaux, chacun avec un rôle précis :

NiveauTechnologieContenuSécurité
Niveau 1 (primaire)MMKV patrimoi_v2Données patrimoine JSON complètesAES-128, clé en Keychain
Niveau 1 (clé)iOS KeychainClé AES-128 de MMKV + JWT Supabase + PIN hashSecure Enclave, WHEN_UNLOCKED_THIS_DEVICE_ONLY
Niveau 2 (legacy)AsyncStorageCopie patrimoine (fallback offline + lazy migration)Non chiffré
Niveau 3 (outbox)MMKV patrimoi_v2Queue mutations, verrou, copie locale la plus récenteAES-128 (même store)

4.1 MMKV chiffré

Deux instances MMKV distinctes sont utilisées :

  • patrimoi_key (id='patrimoi_key', non chiffré) — stockage temporaire de la clé AES-128 avant migration Keychain. Vide post-migration.
  • patrimoi_v2 (id='patrimoi_v2', encryptionKey=<clé AES-128>) — toutes les données utilisateur + outbox queue.

MMKV est choisi car ses lectures sont synchrones (contrairement à AsyncStorage qui impose des await), ce qui simplifie le code des reducers Zustand et évite des race conditions lors du chargement des données au démarrage.

4.2 Keychain iOS

Trois services Keychain sont utilisés, chacun isolé par un service ID distinct :

ServiceContenuAccessible
patrimoi.mmkv.keyClé AES-128 pour MMKV patrimoi_v2WHEN_UNLOCKED_THIS_DEVICE_ONLY
patrimoi.supabase.*Session JWT Supabase (access + refresh token)WHEN_UNLOCKED_THIS_DEVICE_ONLY
patrimoi.pinPIN hashé SHA-256 (<hash>:<salt>)WHEN_UNLOCKED_THIS_DEVICE_ONLY

L'attribut WHEN_UNLOCKED_THIS_DEVICE_ONLY garantit que la clé est absente des backups iTunes non chiffrés et liée à l'appareil physique.

4.3 Phases d'initialisation du stockage

La fonction initStorage() (storage.js) exécute 5 steps séquentiels au démarrage :

StepDescriptionFallback
1 — syncLire __enc_key__ dans MMKV patrimoi_key (clé héritée)Continuer si absent
2 — asyncKC.getGenericPassword('patrimoi.mmkv.key') → utiliser ou migrerif(mmkvKey) → évite data loss (fix scope bug v1.2)
3Si aucune clé trouvée → generateKey() + écriture KeychainMath.random fallback si crypto indisponible
4Ouvrir patrimoi_v2 avec la clé définitivemakeMemStore() si MMKV indisponible
5 — bootMigration PIN legacy → SHA-256:salt (one-shot, flag pin_migration_v2)Silencieux si pas de PIN
Fix critique v1.2 — Préservation de clé (scope bug + fallback)

Sur simulateur ou build Debug sans entitlement Keychain Sharing, KC.setGenericPassword() lance errSecMissingEntitlement (-34018). Dans le catch du step 2, le fallback if (mmkvKey) key = mmkvKey est critique : sans lui, key reste null → step 3 génère une nouvelle clé → patrimoi_v2 s'ouvre avec une clé différente → perte totale des données.

Bug de scope corrigé : mmkvKey était déclaré const dans le bloc try {} — inaccessible dans le catch. Corrigé en hoissant la déclaration (let mmkvKey = null) avant le try.

5.2 Outbox pattern (syncQueue.js)

Toutes les mutations utilisateur transitent par un outbox MMKV avant d'atteindre Supabase. Ce pattern garantit la durabilité des mutations même en cas de coupure réseau ou de crash.

Caractéristiques clés :

  • Coalescing — une seule entrée par userId dans la file (last-write-wins)
  • Debounce 800 ms + worker toutes les 5 s
  • Max 5 retries avec backoff exponentiel (base 1000 ms)
  • Mutations échouées persistées dans outbox_failed_v2 (max 20) + alerte Sentry
  • Verrou optimiste (M008) — RPC save_patrimoine_data détecte les conflits multi-appareils (had_conflict: true)
  • stripMarketData() (R8) — retire cours/taux/variation/bvcUpdated avant l'upsert (données de marché jamais sauvegardées en cloud)

5.3 APIs de données de marché

SourceDonnéeTransportCache

Ces données sont chargées via fetchWithRetry() (3 tentatives, backoff exponentiel). En cas d'indisponibilité réseau, l'app affiche les dernières valeurs cachées. Elles ne sont jamais envoyées à Supabase (R8 — strip avant upsert).

BVC — Architecture GitHub Actions cron

La Bourse de Casablanca ne fournit pas d'API publique. PatriMoi utilise un workflow GitHub Actions (bvc.yml) déclenché toutes les 30 minutes : le workflow scrape les cours officiels et les publie en JSON sur un cache statique. L'app consomme ce JSON via fetchWithRetry(). Cette approche contourne les CORS et évite une Edge Function Supabase dédiée pour la BVC.

5.4 Sentry (monitoring)

Sentry est intégré via un module stub défensif : si le package @sentry/react-native est absent, toutes les fonctions deviennent des no-ops silencieux. Deux protections :

  • Scrubbing PII — les montants (/montant|valeur|total|prix/i) et emails retirés avant envoi
  • Silence entitlement — _isEntitlementError() filtre les erreurs errSecMissingEntitlement (simulateur)

8 Export PDF v1.6

PatriMoi v1.6 propose un export PDF en architecture duale : deux fichiers distincts — PDF Patrimoine et PDF Budget — générés via un module natif iOS (RNPDFExport.m) basé sur WKWebView.

8.1 Architecture duale

La décision de séparer en deux PDF est motivée par une contrainte technique de WKWebView : la génération PDF via createPDFWithConfiguration tronque le contenu à une seule "page de rendu" si le HTML dépasse la hauteur écran avant le scroll. Un unique PDF contenant la totalité des données patrimoine + budget dépassait systématiquement ce seuil.

8.2 Module natif RNPDFExport

RNPDFExport.m est un native module React Native iOS qui expose la méthode generatePDF(htmlString, options, resolve, reject) à JavaScript.

Implémentation :

  • WKWebView offscreen — une WKWebView est créée hors écran (frame CGRectZero) et chargée avec le HTML généré
  • Attente du rendu — webView:didFinishNavigation: déclenche la capture uniquement après le rendu complet
  • createPDFWithConfiguration — génère le PDF au format A4 portrait via l'API iOS native
  • Stratégie scroll-per-page — pour les contenus multi-pages, le scroll est simulé par incréments avant chaque capture de page, forçant le rendu de tous les éléments
  • Export — le PDF est écrit dans le dossier temporaire iOS (NSTemporaryDirectory()) puis partagé via UIActivityViewController
Pourquoi WKWebView et pas react-native-html-to-pdf ?

La librairie react-native-html-to-pdf utilise UIWebView (déprécié iOS 12) ou des approches CoreGraphics sans support SVG. WKWebView + createPDFWithConfiguration offre un rendu fidèle au navigateur (SVG, CSS variables, webfonts), nécessaire pour les graphiques tendances et les badges colorés du PDF Budget.

8.3 PDF Patrimoine

Généré par handleExportPatrimoinePDF() dans PageParams.jsx. Le template HTML (htmlPatrimoine) contient :

  • En-tête : nom utilisateur, date du jour (format dd/mm/yyyy), total patrimoine en DH
  • Répartition : tableau des 8 catégories avec valeur et pourcentage
  • Actifs détaillés : PEA (liste des positions avec P&L), or (grammes × cours), immobilier (par bien)
  • Conseils personnalisés : top 3 recommandations tirées de generateConseils()
  • Score de santé : score global 0-100 sur 4 dimensions (diversification, épargne réglementée, BVC, liquidité)

Fix date v1.6 — Dates ISO avec heure

Les opérations budget stockent les dates en ISO 8601 complet (2026-07-25T23:00:00.000Z). La fonction fmtD(iso) utilisait iso.split('-') directement, ce qui retournait 25T23:00:00.000Z comme fragment de jour — affiché tel quel dans le PDF. Corrigé en tronquant d'abord à 10 caractères : const d = String(iso).slice(0, 10) avant split, garantissant le format dd/mm/yyyy dans tous les cas.

9 Conventions de développement

9.1 Zero Static Imports pattern

Tous les modules natifs sont chargés via require() dans un try/catch, jamais via des import ES6 statiques.

// ✅ Correct — Zero Static Imports
let KC = null;
try {
  const K = require('react-native-keychain');
  if (K?.getGenericPassword) KC = K;
} catch {}

// ❌ Incorrect — import statique
import * as Keychain from 'react-native-keychain'; // crashe en CI

Raison : avec Babel CJS transform (Old Architecture), les import ES6 se compilent en require() qui s'exécutent lors de l'évaluation initiale du module factory. Si un module natif manque (CI, pod non installé), toute la factory avorte et tous ses exports restent undefined.

9.3 setData vs setDataRaw — règle absolue

  • setData(fn) — toute modification des données par l'utilisateur. Déclenche la sync cloud.
  • setDataRaw(fn) — chargement de données depuis Supabase ou données de marché (cours, taux). Ne déclenche pas la sync (évite les boucles write→sync→write).

9.4 Convention de nommage des fichiers

Les fichiers source PatriMoi sont en .js ou .jsx (jamais .ts/.tsx sauf AppNavigator.tsx) pour éviter le shadowing Metro. apply_modifs.command supprime explicitement les .ts/.tsx conflictuels avant chaque déploiement.

Exception : les fichiers dans __tests__/ peuvent utiliser .ts (convention Jest). Metro ne bundle pas __tests__/.

PIN hashing — défense en profondeur

Module pinHash.js : SHA-256 pur JS (zéro dépendance native, synchrone, compatible Hermes), sel aléatoire crypto.getRandomValues(). Format stocké : <sha256_hex>:<salt_hex> (97 caractères). verifyPin() gère les deux formats (ancien + nouveau) pendant la transition post-v1.2.

13 Argumentaire des choix techniques

13.1 React Native vs alternatives

✓ Choix — React Native

Partage de logique métier (calculs, migrations, outbox) entre iOS et un futur client Android. Écosystème mature, Hermes rapide. Itération sur la logique sans recompiler en Swift.

Alternatives écartées

Swift natif — plus performant mais pas de partage de code. Flutter — excellent mais l'équipe est JS-native, et l'accès Keychain/MMKV est plus limité.

13.2 MMKV vs AsyncStorage

✓ Choix — MMKV

Lectures synchrones → pas de await dans les reducers Zustand. Chiffrement AES-128 natif. 10× plus rapide qu'AsyncStorage. API simple.

AsyncStorage conservé

AsyncStorage reste comme couche legacy pour la migration progressive (smartRead : MMKV first, fallback AsyncStorage). Sera retiré en v2.0.

13.3 Keychain pour la clé MMKV

✓ Choix — Keychain

La clé AES-128 dans MMKV était accessible via un backup iTunes non chiffré. Keychain avec WHEN_UNLOCKED_THIS_DEVICE_ONLY lie la clé à l'appareil et l'exclut des backups.

Migration graduelle

Les utilisateurs existants migrent automatiquement à la première ouverture post-v1.2, sans interruption. Phase 2 async de initStorage().

13.4 Supabase vs Firebase

✓ Choix — Supabase

PostgreSQL + RLS = sécurité forte et familière. Edge Functions Deno pour le proxy de marché. Région West EU (RGPD). Open-source = pas de vendor lock-in.

Firebase écarté

Firestore est NoSQL — inadapté à un schéma patrimoine évolutif. RLS PostgreSQL est plus expressif que les règles Firebase pour l'isolation par user_id.

13.5 WKWebView pour le PDF vs react-native-html-to-pdf

✓ Choix — RNPDFExport.m + WKWebView

Rendu fidèle SVG, CSS variables, webfonts — nécessaire pour les graphiques tendances (SVG inline) et les badges colorés. createPDFWithConfiguration produit un PDF A4 natif iOS.

react-native-html-to-pdf écarté

Utilise UIWebView (déprécié iOS 12) ou CoreGraphics sans rendu SVG fidèle. Le SVG des tendances budget s'affichait en boîte noire. Maintien incertain.

13.6 Zustand vs Redux

✓ Choix — Zustand

API minimaliste (20 lignes de store), pas de boilerplate action/reducer/selector. La distinction setData/setDataRaw est plus lisible en Zustand que via des middlewares Redux.

Redux écarté

Redux Toolkit aurait imposé slices, middlewares, RTK Query — overhead disproportionné pour un store mono-entité.

13.7 Navigation maison vs React Navigation

✓ Choix — routeur Zustand

L'app a une navigation tabulaire simple sans deep linking ni stack imbriqué. React Navigation ajouterait ~800 Ko de bundle et une complexité inutile.

React Navigation pour la v2

Si notifications push (deep link → page spécifique) ou back-stack natif sont requis, la migration sera envisagée en v2.0.

13.8 Outbox pattern vs appel direct Supabase

✓ Choix — Outbox MMKV

Un appel direct perdrait les mutations en cas de coupure réseau. L'outbox garantit la durabilité : même si l'app est tuée entre une modification et la prochaine flush, la mutation sera envoyée au prochain démarrage.

Compromis — latence de sync

La sync peut arriver jusqu'à 800 ms après la modification (debounce). Acceptable pour une app de patrimoine personnel où la cohérence éventuelle est suffisante.
